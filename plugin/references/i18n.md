# Internationalization (i18n)

Velk's i18n shipped in four stages — Phase 1, 2, 3, 3b — but it's now one
finished feature; don't treat any part of it as half-built. Three
independent layers, each with its own storage:

1. **Hardcoded UI strings** in theme/core PHP — wrapped in `t()`.
2. **Structural URLs** — item-type/taxonomy slugs and page slugs, so
   `/blog/post-x` can become `/en/news/post-x`.
3. **Per-record content** — title/slug/fields on items, pages, terms; value
   on options — each with a parallel `*_translations` JSON column. All
   three are engine-native — no plugin system, nothing to install.

## Declaring languages

```json
"i18n": {
  "enabled": true,
  "default": "pt-BR",
  "default_label": "Português"
}
```

`i18n.default` is set in `site.json` only — it's not editable from the
admin, since every fallback in the system points back to it. Add the rest
of the languages at `/admin/languages`, each with a `url_prefix` (used by
routing) and a label.

`default_label` (v3.6.0+, **required when `enabled` is true** —
`schema:validate` rejects its absence) is the default language's display
name, shown in the site switcher and the admin's language tabs. It lives in
`site.json` because the default language is the only one with no row in
`languages`: the panel creates *additional* languages and refuses a code
equal to the default. So each language has exactly one owner for its name —
the default's is the theme, the rest belong to the panel. Any string works:
`Português`, `Brasil`, `PT`.

Before v3.6.0 this came from a fixed thirteen-language map inside `I18n`,
which meant the default language's name could not be changed at all. The map
is gone; a theme that omits the key now shows the raw code (`pt-BR`), which
is why validation treats it as an error rather than letting it surface in
production.

Core helpers available everywhere: `lang()` (current code), `lang_is('en')`,
`default_language()`, `available_languages()`, `i18n_enabled()`.

## Hardcoded strings: `t()`

```php
echo t('Read more');
echo t('Hello, {name}!', ['name' => 'World']);
echo t('Post', context: 'noun');   // disambiguate noun vs verb
```

On the default language `t()` returns the input untouched (no DB hit).
Otherwise it looks the string up in a catalog built by `./bin/velk
i18n:scan` (scans theme + core for `t()` calls) and translated inline at
`/admin/translations`. Engine flash messages (`PublicFormController`,
member auth) and `forms.<id>.success_message` from `site.json` are wrapped
in `t()` too, landing in that same catalog.

## URL routing

```
Default language:  /sobre, /blog/post-x, /categoria/tag-x
en (with prefix):  /en/about, /en/news/post-x, /en/category/tag-x
```

**One URL per language (v3.9.0+).** In a non-default language, content
answers at its translated slug — or, with no translated slug there, at its
default slug: no English slug → `/en/sobre`; English slug `about` →
`/en/about`, and `/en/sobre` is a 404. Each level of a hierarchy follows the
rule on its own. When one record's translated slug is another's slug in
that language, the translated one keeps the address (level by level; a
published item always beats a draft) and the other has **no URL** there:
`hreflang` and the sitemap leave that language out for it, the language
switcher sends to the language's home, and the admin warns on save.
`$item->ownsUrlIn('en')` (also `Term`, `Page::ownsUrlIn($key, $config,
'en')`) tells whether a record is the one that answers. Before v3.9.0 the
rule was strict: no translated slug, no URL in that language. `/` always
resolves to the home page regardless of language.

Two things get translated to build those URLs: page slugs
(`pages.slug_translations.en`), and item-type/taxonomy slugs — e.g. `blog`
→ `news` (en) / `noticias` (es) — stored in `config_translations` and
edited via the "Traduções" button at `/admin/items/{type}` and
`/admin/taxonomies/{taxonomy}`.

Template helpers for this layer:

```php
url('/sobre')          // /sobre in pt, /en/sobre in en — only adds the prefix
url('/sobre', 'en')    // explicit language
$page->url()           // a page's URL in the active language, slug translated
lang_url('en')         // current page's URL, in English
lang_switcher()        // [['code','label','url','is_current'], …]
the_html_lang()        // for <html lang="...">
the_hreflangs()        // <link rel="alternate" hreflang="…" …> tags
the_canonical()        // absolute URL of current page, current language
```

## Per-content translation

Items, pages, terms, and settings all follow the same shape: the original
column keeps the default-language value (zero-impact on existing rows and
code), and a parallel `*_translations` JSON column holds everything else.

```
items:    title_translations, slug_translations, fields_translations
pages:    title_translations, fields_translations, slug_translations
terms:    name_translations, slug_translations, fields_translations
settings: value_translations
```

Each model exposes fallback-aware readers — `$item->titleIn('en')`,
`slugIn('en')`, `fieldIn('content', 'en')`, `fieldsIn('en')` (terms use
`nameIn()` instead of `titleIn()`; pages use `slugTranslationFor()` instead
of `slugIn()`) — all falling back to the default column when a language has
nothing. In URLs, a missing translated slug means the default slug (see URL
routing); `hasSlugIn('en')` only says whether the record has its own.

**Templates don't call those directly.** `field()`, `the_title()`,
`option()` — the normal helpers — already resolve to the active language,
falling back to the default automatically. Write a template once against
`field('content')`; it serves every language as translations are filled
in, no template change required.

## Admin translation UI

Items (`/admin/items/{type}/{id}`), pages (`/admin/pages/{key}`), terms
(`/admin/taxonomies/{taxonomy}/{id}`), and options (`/admin/options/{key}`)
all render one language tab per enabled language, on the same form:

- Default tab: the plain inputs (`title`, `slug`, `fields[x]`) — saves to
  the original columns, exactly as before i18n existed.
- Other tabs: the same fields as `title_translations[en]`,
  `slug_translations[en]`, `fields_translations[en][x]`, default value
  shown as a placeholder for context.
- One submit saves every language. A green dot marks tabs that already
  have content.

JSON-defined pages are a special case: the default tab shows title/URL as
read-only (they come from `site.json`) — only custom fields and the
translation tabs are editable.

## The empty-translation contract

Every editor above drops empty translation inputs on save — the detail
that keeps the fallback chain trustworthy. A blank tab leaves no row at
all, so `titleIn()`/`fieldIn()` fall through to the default as if
untouched. Type a value that happens to *equal* the default, though, and
it's saved anyway: non-empty means intentional, kept as a real pin rather
than read as "not translated yet." Empty means untranslated;
present-but-equal means "yes, really this, on purpose."

## Sitemap alternates

`/sitemap.xml` emits `<xhtml:link rel="alternate" hreflang="…" href="…">`
for every URL once i18n is enabled, plus one `hreflang="x-default"` pointing
at the default-language version. Each language gets the URL the router
answers at — translated slug, or the default one — except for a record that
lost a slug conflict in that language, which gets no alternate there.

## Not there yet

- Auto-slug from a translated title — set non-default slugs by hand.
- Auto-translation / LLM-assisted suggestions.
- Per-language email templates — member password-reset is one hardcoded
  language for now.
- `Accept-Language` auto-detection and a language switcher — build one from
  `available_languages()` / `lang_switcher()`; Velk doesn't ship one.

Treat any of these as a real feature-design task if asked for — not a quick
patch.
